# Terraform fidelity

Nimbo imports existing Terraform, lets you edit it on the canvas, and exports
it back. This page states what the round trip guarantees, how it is tested,
what the tests found, and what is still not covered.

## Guarantees

When you import a Terraform root (folder import, template, or code editor)
and export it, the exported folder:

1. **Means the same thing.** Every top-level block survives with its type,
   labels, attributes and nested blocks: resources, data sources, modules
   (including `providers = {}` mappings and `depends_on`), variables (with
   `validation`, `nullable`, `sensitive`, `ephemeral`), outputs (with
   `precondition`, `depends_on`), providers and their aliases, `locals`,
   `terraform` (`required_providers`, `backend`, `cloud`), and every other
   block as is (`moved`, `import` with `for_each`, `removed`, `check`, …).
   Expressions are copied token for token: heredocs (`<<EOT`, `<<-EOT`),
   template directives (`%{ if }`, `%{ for }`), `for` expressions, splats,
   conditionals, `dynamic` blocks, provider-defined functions
   (`provider::aws::arn_parse`), Unicode and escapes.
2. **Is formatted.** Generated files pass `terraform fmt -check`.
3. **Validates** with `terraform init -backend=false && terraform validate`
   whenever the original does.
4. **Plans no changes** against infrastructure the original created (checked
   on the Floci emulator).
5. **Keeps its comments.** `#`, `//` and `/* */` comments stay with the
   attribute or block they belong to: lines above it (file headers included),
   the comment at the end of its line, comments after a block's `{` or `}`,
   commented-out code at the end of a block, and end-of-file comments.
   Comments inside an expression are part of the expression.
6. **Keeps its files.** Everything else in the project folder is copied
   unchanged to the same relative path: Lambda sources, zips, templates read
   by `file()`/`templatefile()`, `.terraform.lock.hcl`, override files,
   `*.tf.json`, a `README.md` or `.gitignore` of its own, and `.tf` files
   holding only comments. Local modules (nested too) are copied to
   `modules/<name>` with their `source` rewritten to match.
7. **Keeps its layout.** Every block is written back to the file it came
   from (`network.tf` stays `network.tf`), in its original order within the
   file, whatever its kind. Several `locals` or `terraform` blocks stay
   separate, each with its own items, where they were (a `backend` in
   `backend.tf` stays there). Blocks added later in Nimbo join the file that
   already holds most blocks of their kind (resources of the same catalog
   category, variables, data sources, …), else the recommended file.
8. **Keeps its variable files.** `terraform.tfvars`, `*.auto.tfvars` and other
   root `*.tfvars` are written back under their own name, so Terraform loads
   them exactly as before; `environments/<name>.tfvars` stay there.
9. **Is stable.** Exporting twice gives byte-identical files, and importing
   an export gives back the same workflow (files and positions included).

What may differ, by design:

- **Inside a block**, attributes come before nested blocks; whitespace
  follows `terraform fmt` (blank lines grouping attributes are kept; an
  empty `{\n}` becomes `{}`). Comments move with their block.
- **Line endings.** CRLF files are read as LF. Inside a heredoc this turns a
  `\r\n` line ending of the value into `\n`, as git's `autocrlf` does on
  checkout.
- **`.env.example`** values are rewritten as `KEY=VALUE`, quoted only when
  needed.
- **Project files added.** The export also writes `README.md` (inputs,
  outputs, resources, providers, from the workflow, and a "State &
  environments" section: where the state lives and that the environments of
  one root share it), `.gitignore` (Terraform working data, state, crash
  logs and `*.tfvars` except `*.tfvars.example`), `terraform.tfvars.example`
  and, for a workflow with a cloud and no `backend`/`cloud` block,
  `backend.tf.example` (that cloud's remote state as a partial
  configuration: S3 with `use_lockfile` and `encrypt`, `azurerm`, `gcs`,
  `oci`; copy it to `backend.tf`), each only when the project has no file of
  that name. They start with a "Generated by Nimbo" line, so importing an
  export regenerates them instead of keeping stale copies. The `.gitignore`
  ignores `*.tfvars` (`*.tfvars.example` excepted) like the standard
  Terraform one: exported variable files can hold sensitive values, so
  committing `environments/<name>.tfvars` is a deliberate `git add -f`,
  explained in the file.

Content Nimbo creates (new workflows, templates, catalog starters, nodes
added by an AI agent) has no recorded file and gets the recommended layout,
recomputed on every export: `versions.tf`, `providers.tf`, `variables.tf`,
`locals.tf`, `outputs.tf`, `data.tf`, one file per catalog category
(`network.tf`, `compute.tf`, `containers.tf`, `storage.tf`, `database.tf`,
`messaging.tf`, `api.tf`, `iam.tf`, `security.tf`, `monitoring.tf`,
`analytics.tf`, `ai.tf`, `devtools.tf`, `cost.tf`) and `main.tf` for module
calls and the rest; a workflow with at most 5 resources keeps its data
sources and resources in a single `main.tf`. Inside those files data sources
and resources follow their dependencies, then their address. In Pro mode the
inspector's **File** field (or MCP `update_node` with `file`) moves a node to
another file; the node then stays there. A code edit (the Code tab, MCP
`apply_terraform_code`, `PUT /workflows/{id}/terraform`) keeps every block
in the file it was written in: blocks written where the recommended layout
puts them stay automatic only while that layout still agrees; otherwise
(e.g. other blocks of their category were written to another file) they
record their file, as does every block of a file holding a recorded block,
so the file keeps its written order. Applying the same code again changes
nothing.

The Code tab also creates, renames, moves and deletes files (one `PUT
/workflows/{id}/terraform` with `changes`/`moves`). A new root `.tf` file
holds the blocks written in it; renaming a file is a move, so its blocks
keep their node IDs, positions and labels (matched by address) and record
the new file; deleting a file removes its blocks. A code file without
blocks (empty but for comments) is kept as a plain file, like a folder
import keeps one, and becomes code again once it has a block; an emptied
one is dropped. Files that are not code (local modules under `modules/`,
templates, scripts, docs) are stored as workflow assets and exported as
they are; edits inside `modules/<name>/` change that module (module views,
lint, export, deploy read the stored files). Empty folders exist only in
the tree until a file is put in them: the backend stores files, never
placeholder files.

## Export layouts

A workflow is exported in one of two directory structures (`layout` on the
workflow; the Export dialog and MCP `update_workflow` set it):

| `layout` | Structure |
|---|---|
| `single` | Everything above: one root module, so **one state**. Environments are variable files of that root (`environments/<name>.tfvars`), so they share its state. Imported projects get this layout and keep their own files. |
| `environments` | The service module plus one root module, and so one state, per environment (below). |
| absent (auto) | `environments` when the workflow has two or more environments, else `single`; `single` too when the environments layout is impossible (an environment name that cannot name a directory, provider configuration reading a resource). |

The environments layout follows the HashiCorp style guide, Google Cloud's
root-module guide and AWS Prescriptive Guidance:

```text
README.md  .gitignore  Makefile
modules/<service>/        the workflow's blocks: versions.tf (required_providers
                          as >= minimums, configuration_aliases), variables.tf,
                          outputs.tf, README.md, no provider configuration
modules/<name>/           the local modules it calls (source "../<name>")
environments/<env>/       backend.tf, backend.hcl.example, versions.tf (the
                          workflow's ~> pins), providers.tf, variables.tf,
                          locals.tf, main.tf, outputs.tf, terraform.tfvars,
                          .env.example, .terraform.lock.hcl
```

- **Service module.** `<service>` is the workflow name in snake_case
  (`Items API` -> `items_api`), or the imported one (`service` on the
  workflow, kept on rename: every address in the states starts with
  `module.<service>`). It holds every resource, data source, module call,
  output and `moved`/`check` block, and only the variables and locals they
  read (a variable or local only provider configuration reads lives in the
  roots alone); `path.root` reads as `path.module`; the workflow's other
  files (Lambda sources, templates) move in with it. A default lives in one
  place: inputs whose value differs between environments have none
  (each root's `terraform.tfvars` sets them), inputs the roots read too
  (e.g. `project` for the provider's default tags) take theirs from the
  root, the others keep theirs in the module.
- **Environment roots.** `main.tf` calls the service module with
  `<input> = var.<input>` for every input some environment sets (a value or
  a `TF_VAR_<name>` environment variable), every input without a default
  and every input the root reads itself, so a value set in an environment
  reaches both the provider and the resources. The provider configurations
  are passed with `providers = {}` when there are aliases. `providers.tf`
  holds the workflow's provider blocks; `variables.tf` (alphabetical) and
  `locals.tf` declare what the root passes or reads. `import` and
  `removed` blocks (only allowed in a root) go to `main.tf` with their
  addresses prefixed by `module.<service>.`. `outputs.tf` re-exports every
  output. `terraform.tfvars` holds the environment's values; values of
  sensitive variables are never written: `.env.example` lists them as
  `TF_VAR_<name>=` next to the environment variables (secret ones blank).
- **State.** Each root's `backend.tf` gives it its own state: the
  workflow's backend (or `cloud` block) with the environment in its key, or
  the default of the workflow's cloud as a partial configuration whose
  storage comes from `backend.hcl` (`backend.hcl.example` shows the
  settings): S3 `key = "<service>/<env>/terraform.tfstate"` with
  `use_lockfile = true` (native S3 locking; `required_version` is raised to
  `>= 1.10`) and `encrypt = true`; `azurerm` `key` the same way with
  `use_azuread_auth`; `gcs` `prefix = "<service>/<env>"`; `oci` `key`
  (Terraform `>= 1.12`); HCP Terraform `workspaces.name = "<name>-<env>"`.
  Other backend types are copied unchanged.
- **Makefile.** `make init|plan|apply|validate ENV=<env>` and `make fmt`
  (`terraform -chdir=environments/$(ENV) ...`, `-backend-config=backend.hcl`
  when that file exists); the README explains the tree, the commands and
  each environment's state key.

The Code tab shows the files of the workflow's layout. What is editable
follows what `PUT /workflows/{id}/terraform` can read back without losing
anything:

- **Service module** `modules/<service>/*.tf`: editable, and files can be
  created, renamed and deleted there. These are the workflow's blocks; each
  stays in the file it was written in (a new `queues.tf` holds its blocks).
  Other files created in `modules/<service>/` are stored as workflow assets
  without the prefix (`modules/<service>/templates/a.tftpl` is the asset
  `templates/a.tftpl`, which the export places back there).
- **Every root's `main.tf`**: editable. A literal module argument written
  there becomes that environment's value (it then moves to the root's
  `terraform.tfvars`, edited in Variables & Environments); the rest of the
  file is regenerated.
- **The first environment's** (alphabetical) `providers.tf`, `versions.tf`
  and `backend.tf`: editable. They are the workflow's provider configuration
  and Terraform settings, which every root shares; the same files of the
  other roots are read-only ("edit `environments/<first>/…`"), because the
  import keeps only the first root's.
- **Derived root files** (`variables.tf`, `locals.tf`, `outputs.tf`) and the
  variable files are read-only with the reason shown: they are rendered from
  the service module and the environment values, so an edit would be lost.
- **Environment roots are fixed**: no file can be created, renamed or deleted
  under `environments/` (environments are managed in the app), and new files
  outside `modules/` are rejected because the layout has no place to store
  them; local modules go in `modules/<name>/`.

The folder
import recognizes the layout: `environments/<env>/` (or `envs/<env>/`)
roots that only call one `modules/<service>` are **one** workflow with one
environment per root (values from its `terraform.tfvars` and
`*.auto.tfvars`, module arguments and `.env.example`), the service module's
blocks as its own, the first root's providers and terraform settings, the
state backend with the environment taken out of its key (dropped when it is
the cloud default) and the first root's lock file. Roots that hold
resources or call other modules stay separate projects, as before. The
sandbox always runs the single root (with its own backend override), so
deploys work the same in both layouts.

## What Nimbo reports instead of guessing

| Situation | Diagnostic | What happens |
|---|---|---|
| `override.tf` / `*_override.tf` | `unsupported_file` (warning) | Not shown on the canvas; kept as a file, exported unchanged. |
| `*.tf.json`, `*.tfvars.json` | `unsupported_file` (warning) | Same. A folder with only JSON configuration is listed as skipped by the scan. |
| A path leaving the folder: `"${path.module}/../x"`, `file("../x")` | `path_outside_folder` (warning) | The file is not copied; fix the path or copy the file into the folder. |
| A local module outside the imported folder | `module_outside_folder` (warning) | Its `source` is kept as is. |
| Environment roots with different provider blocks (environments layout import) | `environment_providers_differ` (warning) | The first root's providers are kept; set what differs per environment with variables. |
| Per-environment state keys without one pattern (environments layout import) | `environment_state_key` (warning) | The key is dropped from the workflow's backend; the next export writes `<service>/<env>/terraform.tfstate` (`gcs`: `<service>/<env>`), so check the keys before `terraform init`. |

## How it is tested

The harness lives in `backend/internal/tfqa`. Every root goes through the
real API: `POST /import` (the folder import, with local module copies) or
`POST /workflows` for templates, then `POST /workflows/{id}/export` with
environments. Checks per root:

| Check | What it verifies |
|---|---|
| `semantic` | Both folders reduced to a canonical form (`tfqa.CompareDirs`): top-level blocks by type and labels, attributes by name with expressions compared token by token, nested blocks in order, `locals` and `terraform` merged; local module calls followed into both copies and compared the same way; override and JSON files compared too. It ignores only file split, top-level block order, attribute order and whitespace. |
| `comments` | The multiset of comments of every `.tf` file (root and modules) is unchanged. |
| `reimport` | Importing the export gives the same workflow (nodes, variables, outputs, locals, providers, terraform, other blocks, environments, edges, comments, and every block's file and position). Templates are compared at the file and position their export gave them. |
| `stable` | Two exports are byte-identical. |
| `files` | Every non-Terraform file of the root and its modules is in the export, byte-identical, at the same relative path. |
| `layout` | Imported roots: each root `.tf` file of the export holds exactly the top-level blocks of the original file of that name, in the same order (every `locals` and `terraform` block with its own items), and the export adds no `.tf` file. Templates: only recommended file names, plus `README.md` and `.gitignore`. |
| `tfvars` | Every root and `environments/` variable file is in the export at the same path with the same values. |
| `fmt` | `terraform fmt -check -recursive` passes on the export (copied module files only need to be as formatted as their originals). |
| `validate` | `terraform init -backend=false` + `validate` pass for the export whenever they pass for the original. |
| `deploy` | Apply the original on Floci, swap in the export in the same working directory, `terraform plan -detailed-exitcode` must report no changes, or exactly the changes the original itself plans right after its apply (attributes the emulator does not round-trip). |

`tfqa.CompareDirs` has its own tests showing it catches changed values,
missing blocks, nested changes, duplicate locals, module content changes,
lost comments and stray override files.

The **environments layout** has its own check, `TestEnvironmentsLayout`, on
every catalog template given `dev` and `prod` environments (through the same
API): `tree` (no root module at the top, a service module without provider
blocks, per environment a backend with its own key, a call of the service
module and `terraform.tfvars`), `stable` (two exports byte-identical),
`reimport` (the folder import of the export is one workflow with both
environments, and its export is the same tree, byte for byte, READMEs
aside: they show the description, which the tree does not carry) and
`validate` (`terraform init -backend=false` + `validate` in each
environment root). The `docker`-tagged catalog tests validate every
environment root inside the `hashicorp/terraform` container and deploy the
`dev` root of `aws-serverless-api` to Floci (apply, call the API, empty
plan, destroy).

```sh
cd backend
# Always runs (part of go test ./...): templates, existing fixtures, the
# vendored corpus subset and the edge-case root (+ CRLF, tab and 1,500-block
# variants). fmt runs when terraform is on PATH; TFQA_VALIDATE=1 adds validate.
go test ./internal/tfqa/

# Full corpus: clones the pinned repositories, runs every check including
# validate (downloads providers), then the Floci deployment check (docker).
TFQA_PLUGIN_CACHE=/tmp/tf-plugins go test -tags corpus -timeout 4h ./internal/tfqa/ -v

# Environments layout in the terraform container and on Floci.
go test -tags docker ./internal/catalog/ -run TestEnvironmentsLayout -v
```

Environment: `TFQA_CORPUS` (clone cache), `TFQA_PLUGIN_CACHE` (provider
cache kept across runs; by default each test run uses a temporary one),
`TFQA_VALIDATE=0|1`, `TFQA_REPORT`, `TFQA_REPORT_LOCAL`,
`TFQA_DEPLOY_REPORT` (result tables), `TFQA_KEEP` (keep exports).

### Module extraction and inlining on Floci

`TestModuleRefactorDeploy` (`-tags corpus`, `tfqa/modules_deploy_test.go`)
applies an AWS template on Floci, extracts a group of its nodes into a local
module through `POST /workflows/{id}/modules/extract`, swaps the export in
(state kept) and requires `terraform plan` to only move resource instances
into `module.<name>` (`0 to add, 0 to change, 0 to destroy`), applies it and
requires a clean plan; then it inlines the module back (`POST
…/modules/{node}/inline`) and checks the same in the other direction.

```sh
go test -tags corpus -timeout 40m ./internal/tfqa/ -run TestModuleRefactorDeploy -v
```

## Bugs found and fixed

| Bug | Before | After |
|---|---|---|
| Comments dropped | Import dropped every comment: 600 comments lost across 45 of the 48 public roots (only 3 roots had none to lose). | Kept on attributes, blocks, `locals`, `terraform` and file ends (`model.Comments`); 0 lost. Mirrored in the desktop types; canvas edits keep them. |
| Dependency lock file dropped | The folder import skipped `.terraform.lock.hcl` (8/48 roots), so the export resolved newer providers. | Kept as an asset and exported (the sandbox still ignores it). |
| Variable files moved | `terraform.tfvars` and `prod.auto.tfvars` were exported as `environments/default.tfvars` / `environments/prod.tfvars`, which Terraform does not load automatically: a plan of the export saw different inputs. `terraform.tfvars` + `terraform.auto.tfvars` were merged into one environment. | Each root variable file is its own environment remembering its file (`Environment.File`) and is written back under that name; name clashes get the file name. |
| Override files merged as normal blocks | `override.tf` was imported as a second `resource "aws_security_group" "web"`: a `duplicate_address` error and an export with two copies of the block, which does not validate. | Not interpreted (`unsupported_file` warning), kept as a file and exported unchanged, so Terraform applies it as before. |
| JSON configuration silent | Folder imports copied `*.tf.json` without saying anything; folders with only JSON configuration vanished from the scan. | `unsupported_file` warning on the scan and the workflow; JSON-only folders listed as skipped. |
| Mixed line endings | CRLF files kept `\r\n` inside multi-line expressions and heredocs (35 CRs in the edge root's `main.tf`) while the rest became LF. | CRLF is read as LF everywhere. |
| Files outside the folder | References such as `"${path.module}/../fixtures/app"` silently broke in the export. | `path_outside_folder` warning on the scan and the workflow. |
| Module problems hidden after import | Diagnostics of copied local modules were shown by the scan only. | Also on the imported workflow. |
| File layout lost | Every import was regrouped into `versions.tf`, `providers.tf`, `variables.tf`, `main.tf` and `outputs.tf`: `network.tf`, `iam.tf`, `lambda.tf`… disappeared, blocks were reordered by kind, a file's header comment could end up in the middle of `main.tf`, several `locals`/`terraform` blocks were merged into one (the edge root lost its own `versions.tf`/`backend.tf` split), and comment-only files were folded into the next file. | Every block keeps its file and source position (`File`/`Order` in the model); each `locals`/`terraform` block is a `BlockPart` its items point to; comment-only files are kept as they are. Checked by `layout` on every root. |

## Known limitations

- Comments inside a `*.tfvars` file and in `.env.example` files are not kept
  (environment values are a map).
- Comments between an attribute name and its value (`a = # x` + newline + value)
  are dropped.
- A block moved to another file (inspector **File**, `update_node`) or added
  to an imported file is written after the blocks imported into that file;
  data sources, resources and module calls among them follow their
  dependencies, then their address.
- Files outside the imported folder are reported, not copied.
- Override files and `*.tf.json` are kept and exported, but not shown or
  editable on the canvas; deleting a block on the canvas that an override
  file still targets makes the configuration invalid.
- A local module whose directory name clashes with an asset folder under
  `modules/` of the root shares that folder.
- Deployment equivalence covers AWS on Floci only; Azure, GCP and OCI roots
  are covered by the semantic, `fmt` and `validate` checks.
